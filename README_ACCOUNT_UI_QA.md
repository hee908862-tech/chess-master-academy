# 종합 QA 후 계정 상태·훈련 설명·반응형 UI 수정

기준 main: `0b315a3c4568628d2f5fe9160b0800be3218b5bc`. 검토용 PR이며 병합·배포하지 않는다. 운영 계정(특히 QA20261019FRESH), 운영 PIN, 운영 기록에 접근하거나 초기화하지 않았다. 모든 삭제 검사는 임시 SQLite/일회성 PostgreSQL의 가짜 계정으로 수행했다. 운영 초기화 실패의 실제 원인은 여전히 미확정이다.

## 변경과 데이터 보존

- 초기화가 `progress`만 비워 현재 진단·훈련 기록을 남기던 불일치를 해결한다. 로그인 토큰·현재 PIN·정확한 확인 문구와 `/me`의 `reset_revision`을 요구한다. 세 저장 영역을 한 트랜잭션에서 비우며 기본 progress를 생성하고 마지막에 계정 세대 번호를 올린다. 계정·PIN·세션·문제은행·기기 설정은 보존한다. 화면도 이 범위를 명시한다.
- `account_generations`는 새 보조 테이블이다. 시작 시 기존 JSON/계정/세션을 다시 쓰지 않는다. 행이 없는 기존 계정은 세대 0으로 읽는다. HTTP 요청의 인증 계정/세대를 ContextVar로 전달하고 쓰기 전에 확인한다. PostgreSQL은 계정 초기화 advisory lock을 evidence lock/row lock보다 먼저 잡고, SQLite는 기존 단일 writer 트랜잭션을 사용한다. 초기화 전에 시작된 요청의 뒤늦은 쓰기는 409다. 동일 revision의 재전송도 409이며 새 기록을 다시 지우지 않는다. 외부 DB 호출은 middleware의 이벤트 루프가 아닌 스레드에서 수행한다.
- 초기화 요청은 30초 클라이언트 대기 제한을 적용한다. 취소·저장 중·실패와 불확실한 완료를 구분하고 버튼을 복구한다. 성공 후 페이지 재로드로 각 모듈의 옛 보드를 제거한다. 구형 클라이언트의 revision 없는 요청은 검증 오류가 되므로 새 화면을 불러와야 한다. 운영 백업 복원 기능을 추가하지 않는다.
- `refresh()`와 대국 복원은 계정 전환 후 늦게 온 응답을 적용하지 않는다. 늦은 401이 새 토큰을 지우지 않는다.
- 새로운 훈련 시도에 `current_helped/current_hint_level`, 시작 시 같은 카드의 **당일** 도움 노출 `prior_helped/prior_help_known`을 추가한다. 기존 `helped/status/independent_kind` 정책은 유지한다. 과거 결과를 재분류하지 않으며 시작 정보가 없는 진행 세션은 과거 도움을 안다고 단정하지 않는다. 상황 성공은 엔진 평가 유지 기준 충족이며 대국 승리와 구분한다.
- 훈련 대시보드 GET은 SELECT만 한다. 옛 카드의 누락 태그는 응답용 복사본에서 보완하고 다음 정상 쓰기 때 기존 방식으로 저장한다. 카드 목록은 50개씩 이전 기록을 조회하고, 복습 목록은 50개와 전체 건수를 반환한다. 전체 JSON 읽기와 능력 집계의 선형 비용은 남으며 DB 구조를 대규모로 바꾸지 않았다.

## UI

320/360/390/430/768/1280 CSS 픽셀 폭을 개발 환경 Chromium에서 에뮬레이션한다. 물리 기기 검증이 아니다. 진단·훈련 보드, 긴 한국어/날짜/UCI·SAN/계정 코드, 가로 넘침을 검사한다. 좁은 화면 버튼은 세로로 배치하고, 하단 메뉴는 한 줄 스크롤로 보드 가림을 줄인다. 좌표와 한국어 기물명·색·선택·직전 수 접근성 이름, 키보드 포커스를 제공한다. 작은 화면에서 체스판 한 칸은 44px보다 작을 수 있으며 일반 동작 버튼은 최소 44px이다.

진단 안내는 기본 안내형과 단서 비공개 재평가를 구분한다. 실제 제출한 수와 원본 기준 수를 구분하고, 대체 메이트 포함 실제 완료 수순에는 실제 수순 라벨을 붙인다. 마지막 문항은 ‘결과 보기’다. 저장/엔진 대기와 단계 비활성 이유, 일반 사용자용 오류 보고 안내를 정리한다. 검증되지 않은 전략 해설·외부 레이팅·교육 효과 주장은 추가하지 않는다.

## 검증 범위와 제한

실제 Docker 이미지·일회성 PostgreSQL 17, 로컬 TCP 응답 유실 및 프로세스 재시작 복구, 실제 Chromium을 사용한다. 기존 225개 통과를 재사용하지 않는다. 최종 회귀 수와 정확한 이미지/커밋은 PR 검증란에 기록한다. `docs/qa-responsive`에는 새 스크린샷과 이미지 HTTP 측정값을 보존한다.

운영 PostgreSQL과 플랫폼 cold start, 운영 데이터 규모·기기별 브라우저는 별도 배포 후 검증 대상이다. 세대 가드는 이 버전의 HTTP 쓰기에 적용된다. 배포 중 구형 프로세스가 혼재하는 시간에는 구형 코드가 이 가드를 사용하지 않으므로 초기화 검증은 전체 교체 완료 후 수행해야 한다. 본 작업은 운영 초기화를 실행하지 않는다.

### 이번 실행에서 발견하고 보완한 항목

- 최초 새 회귀에서 초기화 후 progress 행을 제거한 채 두면 기본 상태와 CAS 기준이 달라 첫 저장이 409가 됐다. 같은 초기화 트랜잭션에서 빈 기본 progress 행을 다시 생성하도록 수정했다.
- 한국어 기물명·직전 수 접근성 이름 도입 후 기존 영문 이름 문자열 검사가 실패해 새 의미를 검증하도록 변경했다.
- 전체 회귀에서 1366×768의 진단 보드가 화면 아래로 벗어나는 문제, 연결 훈련 전용 로딩 안내를 일반 저장 안내가 덮는 문제를 찾아 수정했다. 진단 브라우저 7개 재검사 통과.
- 이미지 HTTP 검사 최초 호출은 서버 준비 전 연결이 끊겼고, 이후 재시작 검사에서는 10초 준비 대기가 부족했다. 정상 기동 로그와 OOM=false를 확인하고 최초 기동/재시작의 준비 대기를 100ms 간격 600회 재시도로 확대했다(개별 HTTP 요청 timeout은 별도). TLS 검증 해제나 운영 설정 변경은 하지 않았다.

- 모바일 프리무브 검사의 고정 300ms 대기에서 전체 실행 1건이 실패했고 단독 실행은 통과했다. 실제 다음 요청 도착을 최대 5초까지 기다리도록 바꾸되 요청 수·수순·session/FEN 검사는 유지했다.
