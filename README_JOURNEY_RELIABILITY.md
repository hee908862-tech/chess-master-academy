# 진단 준비 격리와 수행 근거 안내

기준 main: `a70558bc291790b00ea6a5ca3ae17655f2337a24`. 별도 수정 브랜치/초안 PR이며 main 병합, 운영 배포·설정 변경·재시작·운영 DB 쓰기는 하지 않았다. 계정, 원본 학습 기록, 40,721개 문제 원본은 보존한다.

## 실제 재현과 수정

운영 사용 보고는 진단 첫 시작 약 160초와 그동안 계정/튜토리얼/새 대국 요청 대기다. 이 시간 자체와 PostgreSQL 내부 대기는 로컬에서 확정하지 않았다. 기존 실제 `server.db()`와 인증을 쓰는 새 프로세스/임시 SQLite에서는 코퍼스 준비 11.83초가 전역 RLock으로 둘러싸인 트랜잭션 안에서 실행되어 다른 계정 요청도 11.87~11.90초 대기했다. RLock은 재진입 가능하므로 같은 스레드의 중첩 DB 호출 자체를 교착이라고 판단하지 않는다.

- 이미지 빌드 때 전체 합법 수순·국면 인덱스를 만든다. 원본 SHA256와 정책 버전이 맞을 때만 읽는다. 인덱스 누락/손상/불일치 시 단일 준비 작업으로 복구하고 중복 준비 요청은 503/Retry-After로 안내한다. 실패는 캐시하지 않는다.
- 진단 후보 준비, 기록 국면 순회, 후보 선정과 예약 계산을 DB 쓰기 트랜잭션 밖으로 옮겼다. 선정 전후의 진단/외부 기록 스냅샷을 기존 원자적 저장 게이트 안에서 재확인하며 충돌은 409로 재조회하게 한다. 전체 수순 교집합 제외는 유지한다.
- 프로세스 전역 DB I/O mutex를 제거하고 요청별 연결을 사용한다. SQLite BEGIN IMMEDIATE, PostgreSQL 계정 advisory/row lock, 기존 progress 필드 CAS와 대국별 직렬화는 유지한다. 계정 등록은 PIN 해시 계산을 트랜잭션 밖에서 하고 고유키 위반만 중복 계정으로 처리한다.
- SQLite 쓰기 대기 2초, PG connect 5초/lock 2초/statement 8초로 제한한다. 잠금/일시 연결 실패는 503과 재조회 안내로 반환하고 rollback한다. 메모리의 제한된 익명 타이밍 버퍼로 연결·트랜잭션·쓰기 게이트 대기를 구분한다. 사용자 데이터나 토큰을 로그에 남기지 않는다.
- 앱의 진단·훈련·계정·튜토리얼 요청은 30초 뒤 재조회 안내를 한다. 구형 v8 시작/상태 요청의 60초 설정은 보존한다. 저장 후 응답이 끊길 수 있으므로 실패를 즉시 재전송하지 않는다.

SQLite 자체의 단일 writer와 학습 엔진 작업의 기존 트랜잭션은 남아 있다. 모든 쓰기가 무대기라는 의미가 아니다. 운영 PostgreSQL과 네트워크/플랫폼 cold start는 별도 배포 후 확인해야 한다.

## 사용자 흐름과 측정 경계

| 항목 | 적용 범위 |
|---|---|
| 진단 → 원본 훈련 | 한 번의 클릭/요청에서 경로와 첫 활성 문제를 원자적으로 만든다. 같은 요청은 같은 경로/착수를 반환한다. 다른 미완료 경로는 409로 보존하고 이어하기를 제공한다. 로딩 즉시 예전 보드를 비우고 중복 클릭을 막는다. |
| 홈 | 기록 없음, 준비 중, 진단 진행, 훈련 진행, 결과, 재평가 가능 상태에 따라 기본 행동이 바뀐다. |
| 결과 | 관찰한 수행 → 불확실성 → 다음 연습 한 가지. 식별자/버전/태그/원본 근거는 접힌 영역, 시간은 읽기 쉬운 현지 표기로 표시한다. 근거 보드는 펼칠 때만 그린다. |
| 추가 확인 | 최근 완주 관찰에 따라 원본 난도 600–1200, 900–1500, 1200–1800 중 한 범위의 새 국면 3개를 고른다. 표본 부족/미검증을 약점으로 판정하지 않는다. 심리측정 난도 보정은 아니다. |
| 단서 비공개 재평가 | 평가 중 역량명/난도/전체 수순 길이를 숨긴다. `uncued_execution`은 안내형 `cued_execution`과 분리한다. 상대 응수를 본 뒤 실행하는 과제이므로 머릿속 선계산이나 실전 탐지를 측정했다는 주장은 하지 않는다. |
| 미검증 대안 | 실패/약점 분모에서 제외하고 비교 연습으로만 제안한다. 실제 체크메이트 대안은 계속 규칙으로 인정한다. 메이트 목표의 스테일메이트만 규칙으로 확인된 미달성으로 기록한다. |
| 지연 재평가 | 기존 새 적용 시도 + 마지막 관련 노출 후 7일을 유지한다. 준비 날짜, 마지막 노출, 사유, 추가 복습의 날짜 연장 효과와 대안을 제공한다. |
| 노출 | 새 `journey-v3`/`app-tracking-v1` 기록은 앱 내 새 국면 수행을 별도로 센다. 구형 기록/앱 밖 노출 불명을 기존 독립 근거로 승격하지 않으며, 이것이 이후 앱 내 관찰을 영구적으로 0으로 만드는 것도 막는다. 알려진 ID/전체 수순 중복은 새 앱 관찰에서 제외한다. |

새 엔진 대안 비교 API는 추가하지 않았다. 미검증 수의 전략적 이유나 열세를 만들어 내지 않으며 원본 수순/기존 훈련의 엔진 기능만 제공한다. 원본 외 모든 합법 대안의 평가, 교육 효과, 일반 전략·종반 능력, 외부 Elo는 지원/검증 범위가 아니다. 구형 결과는 재채점하거나 덮어쓰지 않는다.

## 재현 방법과 성능 근거

프로젝트 requirements에 더해 pytest/httpx/playwright 및 Chromium이 필요하다. 모든 실행은 운영 DATABASE_URL을 비우고 fixture가 만든 임시 SQLite만 사용한다.

```sh
CMA_JOURNEY_INDEX=/tmp/chess-journey-index.json.gz python build_journey_index.py
DATABASE_URL='' CMA_JOURNEY_INDEX=/tmp/chess-journey-index.json.gz python scripts/benchmark_journey.py
DATABASE_URL='' CMA_JOURNEY_INDEX=/tmp/missing-index.gz python scripts/benchmark_journey.py
DATABASE_URL='' STOCKFISH_PATH=/tmp/chess-stockfish/usr/games/stockfish CMA_JOURNEY_INDEX=/tmp/chess-journey-index.json.gz python -m pytest -q tests
```

실제 서버 DB/auth, 실제 코퍼스, in-process HTTP TestClient, 세 임시 계정, 새 프로세스별 단일 측정이다. A의 첫 시작 준비 진입 후 B의 `/me`, `/onboarding`, `/game/new`를 동시에 요청하고 C로 warm start를 측정했다. 네트워크/운영 레이턴시나 P95를 의미하지 않는다. CPU 부하 차이도 있으므로 정밀한 속도 배율 주장은 하지 않는다.

| 수정 전 | 11.907 / 11.833초 | 0.062초 | 11.900 / 11.883 / 11.871초 |

## 회귀 증거와 남은 검증

`test_runtime_isolation.py`는 실제 서버 DB/auth에서 느린 준비 중 다른 계정 세 요청, 준비 실패/재시도, 인덱스 적합/불일치, 실제 SQLite 쓰기 경합/복구, 교차 모드 동시 예약, CAS 충돌을 검증한다. `test_journey_guidance.py`는 미검증/미응답 분모, 과거 불명과 앱 내 추적 분리, 버전/안내 조건 분리, 난도 선택, 관련 재노출에 따른 날짜 연장을 검증한다. 기존 journey/bridge 회귀는 단일 클릭 활성화와 단서 비공개 경계를 추가한다.

PC 1366×768/모바일 390×844 Chromium 실제 로컬 API는 진단 저장/재개 → 전 문항 건너뛰기 → 성공 0/미응답 결과 → 원본 훈련을 확인한다. 전체 수순 정답 완주는 API 테스트로 별도 검증한다. 추가 제어 응답 브라우저 테스트는 기존 완료 보드 제거와 중복 클릭 억제를 확인한다. 캡처는 `docs/qa-reliability/`에 보존한다.

### PR #6 추가 검토: 난도 선택의 범위·버전 경계

`additional_plan`은 요청한 `measurement_scope`를 필수 인수로 받으며, 현재 `journey-v3`와 `competency-v2`에 모두 일치하는 같은 범위의 실제 관찰만 사용한다. 구형·미기록·미지원 미래 버전, 다른 안내 조건, 해당 영역의 빈 행은 제외한다. 호환 근거가 없으면 명시된 기본 난도 600–1200으로 시작한다. 이전 기록을 재작성하거나 삭제하지 않는다.

상태 API의 추가 확인 안내는 안내형(CUED)을 명시한다. 출제 API는 요청 모드로 범위를 한 번 정해 난도 선택과 저장된 세션에 동일하게 사용한다. 따라서 안내형 추가 확인과 단서 비공개 재평가가 서로의 완료 결과로 난도를 바꾸지 않는다.

두 범위 결과의 정순/역순, 반대 범위만 있는 경우, 구형·미기록·미지원 버전, 호환 관찰 뒤의 비호환 최신 결과를 검사한다. SQLite/API 회귀는 두 순서 × 두 모드에서 상태 안내와 실제 선정 문제의 난도 구간·저장 범위를 확인하며 7일 재평가 게이트를 우회하지 않는다. 관련 소비 경로도 제한적으로 확인했다: 결과 누적은 이미 보고서 버전/범위로 분리하고, 학습 능력 집계·우선순위는 역량 버전/학습 범위로 분리한다. 특정 진단 원본을 연습으로 여는 경로는 난도 집계와 달라 그대로 유지한다.

위 205개 전체/6개 추가 검증은 이전 head의 이력이다. 이번 보완은 코드·테스트·이 설명을 커밋한 뒤 **해당 최종 커밋에서 전체 `tests`를 다시 실행**한다. 정확한 실행 SHA, 통과/실패 수, 경고와 정적 검증 결과는 PR 검증란과 완료 보고에 기록한다. 병합·배포 및 운영 PostgreSQL 검증은 수행하지 않는다.
