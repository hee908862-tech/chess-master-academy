# 초기 진단 연속 진행과 유한 보충

## 사용자 흐름

초기 진단은 6분야 × 기초/응용 × 각 4개 유효 관찰(48)을 확인하는 한 과정이다. 내부 세션은 최대 8문항으로 유지한다. 마지막 해설에서 ‘다음 문항 · 계속하기’를 누르면 저장 응답과 최신 조회를 확인하고 다음 부족 분야로 이어진다. 별도 메뉴에서 다시 시작하지 않는다. ‘나중에 하기 · 저장하고 홈으로’는 원래 세션을 보존한다. 재접속/새로고침만으로 새 묶음을 생성하지 않는다.

현재 문항의 피드백 확인 전 전체 ‘완료’를 표시하지 않는다. 확인된 관찰 수와 현재 분야의 내부 저장 묶음 진행은 별도로 표시한다. 완주해도 마지막 피드백을 확인하고 다음을 누르기 전에는 active 세션이 있으므로 ready 상태가 아니다.

비동기 주의: 마지막 답안 저장 후 기존 pendingLoad가 실행되고 있을 수 있다. 연속 시작은 이를 기다리고 확정 조회를 한 뒤 진행한다. 토큰/경로가 바뀌거나 조회 실패/시간 초과이면 새 출제를 하지 않는다. 중복 클릭과 실패 후 새로고침으로 중복 출제하지 않는다. 기존 요청 제한도 그대로다.

## 유효 관찰과 상한

- 정상 완료뿐 아니라 검증된 오답/스테일메이트도 유효 관찰이다. 성공 수만으로 48을 채우지 않는다.
- 건너뛰기, 부분 수행, 힌트·도움, 기출, 재시도, 반복, 기술 실패, 탐색 한도 미확정을 별도로 표시한다. 제외 조건 자체와 점수 산식은 완화하지 않는다.
- 새 과정은 기존 24개 일반 대체 외에 명확한 엔진 실행 실패/사용 불가/슬롯 대기 실패를 별도 최대 8개까지 보충한다. 엔진 깊이 부족이나 메이트 증명 탐색 예산 초과는 기술 장애와 다르므로 이 예산으로 인정하지 않는다.
- 8개 기술 보충과 아래 8개 사용자 보충은 저자가 정한 유한 운영 상한이다. 통계적 정확도나 교정된 능력 추정을 뜻하지 않는다. 기존 과정의 저장된 예산 정책은 읽기 시 소급 변경하지 않는다.
- 자동 이어하기는 선택한 부족 분야가 고갈돼도 다른 부족 분야에 공급이 있으면 진행한다. 직접 고른 분야만 고갈된 경우 전체 과정을 거짓 완료/보류로 바꾸지 않고 다른 부족 분야를 안내한다.

## 보류된 과정의 명시적 보충

‘남은 진단 이어하기 · 새 문제 확인’은 한 번의 명시적 보충 요청이다. 서버는 동일 corpus, 활성 세션 없음, 부족 분야/난도와 미노출 재고를 검증한다. 재고가 없으면 409와 이유를 반환하고 아무 기록도 변경하지 않는다. 공급이 있는 필수 슬롯 수에 따라 최대 8개를 추가 배정한다. 대체 상한을 무한히 새로 주지 않으며 이 보충 중 기술 실패가 생겨도 해당 보충의 hard cap을 늘리지 않는다.

보충을 시작하면 원래 frozen baseline, 그 당시 계산된 baseline ID/표시, reviewed_at, 과정 설정을 history에 보존한다. 새 결과는 새 frozen_at과 baseline ID를 가진다. 원본 진단 결과·답안·점수·예약 문항은 유지한다. 결과 상세에서 보존한 이전 결과의 시점/관찰 수/부족 수/당시 수치를 확인할 수 있다. 기존 추천 훈련의 baseline 연결 규칙도 유지되므로 옛 완료만으로 새 과정의 훈련 완료가 되지 않는다.

이전 저장 수순 정책과 새 목표별 대체 수 정책은 출처마다 표시한다. 혼합 기준선은 수행 수치를 보존하되 performance.comparable=false, comparison_allowed=false로 같은 조건의 과거 성장 비교를 차단하고 화면에도 알린다. 새 점수 상수나 Elo 연계를 도입하지 않는다.

## 검증과 한계

로컬 SQLite 합성 기록으로 46/48 보류를 재현해 원래 기준선 보존·실제 재고 2개 배정·반복 요청 거절·재고 없음 무변경을 검사했다. 실제 TEST3의 원인을 확인한 결과가 아니다.

실제 로컬 API + Chromium으로 마지막 묶음 Next→다음 분야, 이중 클릭 1회 생성, 명시 중단/새로고침 복원, 시작 503 후 자동 재시도 없음, 노출 이력 저장 실패 시 진단 시작/제출 차단을 검사한다. 화면 크기는 에뮬레이션이며 운영 브라우저나 실제 휴대폰 검사가 아니다. 기존 48 완주 자동조작은 실제 요청 제한을 존중하도록 착수 간 1.5초를 둔다. 이는 성능 측정값이 아니다.
